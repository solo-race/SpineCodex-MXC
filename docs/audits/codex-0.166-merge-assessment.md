## Highest-risk integration findings

1. **Spine Spawn and agent control** — `core/src/agent/control.rs` and `control/spawn.rs` both conflict. The 0.166 upstream spawn module has been substantially reorganized (0.164 upstream 1,579 lines; 0.166 upstream 1,106 lines), with history preparation moved to `agent/history.rs`; the fork's spawn module is 2,008 lines. The fork's reservation, owner/lineage and branch-specific execution behavior must be preserved when adapting to upstream's new lifecycle.
2. **Sampling loop / context compilation** — `core/src/session/turn.rs` conflicts. The 0.166 upstream sampling success path now handles a tuple including `notify_messages`; the fork uses a custom `SamplingRequestSuccess` result to carry the original input. Both paths must be reconciled. A successful textual merge does not establish correct SpineTree context compilation.
3. **Thread history and resume** — `core/src/session/rollout_reconstruction.rs`, four `thread-store` files, and `rollout/src/policy.rs` conflict. The history projection and reconstruction paths are relevant to resume/replay; older Spine sessions must be tested after integration.
4. **TUI agent state** — `tui/src/multi_agents.rs` conflicts. Upstream changed `spawn_request_summary`'s parameter from `ThreadItem` to `ThreadItemPayload`, while the fork adds SpineTree-related rendering and spawn-status behavior. Model selection, event handling and agent-picker functionality need targeted verification.
5. **App-server and protocol** — `message_processor.rs`, `thread_lifecycle.rs`, `thread_processor.rs` and protocol event/item types conflict. The two binary `*.json.zst` schema assets and generated SDK/types should be regenerated from the resolved protocol source rather than manually editing generated bytes.
6. **Workspace and build** — `codex-rs/Cargo.toml` conflicts because the fork adds `spine-core` and other integration dependencies. Retain Spine workspace members while accepting required 0.166 changes, then compile.

## Findings that reduce effort

- **Windows MXC SystemRoot fix is upstream**: official 0.166 already includes the same `SystemRoot` environment allowlist and workspace-write regression test as fork PR #1. This fix does not need to be independently re-ported; still verify Windows MXC with the integrated build.
- `codex-rs/models-manager` is **not among the 47 Git-conflicted paths**. The hard work is in the runtime and TUI integration, not model registration.
- Official 0.166's *bundled* model catalog does not yet contain GPT-6.2, although the 6.2 rows declare `minimal_client_version: 0.166.0`. If OpenCodex supplies a complete compatible catalog, model selection can be tested without increasing the Spine upstream target beyond 0.166.

## Assessment / go-no-go

**Feasibility:** technically feasible with a meaningful integration effort. The practical risk is high enough that this is not a metadata-only or routine dependency update. Resolving 47 textual merge conflicts is just the first gate; compile errors and functional regressions are not yet measured.

**Scope-limited acceptance conditions for a later implementation:**

1. Resolve all Git conflicts with SpineTree/Spawn ownership, context compilation, and history behavior preserved.
2. Build the Linux and Windows CLI targets and pass the existing focused Spine tests for Spawn, replay, compaction and event rendering.
3. Verify an existing Spine conversation can resume; spawn and completion return correct output without losing parent context.
4. Verify GPT-6.2 Sol/Astra model selection, effective reasoning level, and an actual Responses turn using an authorized account, including one tool call.
5. Verify Windows MXC launch and filesystem helper (including `SystemRoot`) against the resulting binary.

**Recommendation:** treat it as a separate upstream rebase/migration feature. Perform conflict resolution and compilation on that branch before deciding whether the full cross-platform regression work is justified. Do not merge an unresolved upgrade into `main`.
